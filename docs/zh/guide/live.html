实时观测 ​

实时观测页面展示你的其他工具到底在向 Ollama 发送什么：VS Code Copilot、Open WebUI、Continue、n8n、一段 Python 脚本。逐轮呈现，连同缓存保留了什么、丢弃了什么。

侧边栏项目： 实时观测（缓存实验室上方） 路由： /live新增于： v0.7.2（2026 年 10 月） 要求： 无需额外安装。观测端口随 LLMxRay 一起打开。缓存数字需要 Ollama 0.33.3 或更新版本，因为是它在报告这些数字。

有什么用？ ​

LLMxRay 的其他每个页面观测的都是 LLMxRay 自己产生的流量。这个页面观测的是你无法控制的流量：Copilot 在你 GPU 上跑的代理循环、你团队用的聊天前端、每小时调用模型四十次的工作流。

本地环境正是在这些客户端上悄悄变慢的。一个编程助手在你敲下第一个字之前就发送了几千个 token 的指令和工具定义，把编辑器状态放在提示词开头附近，并且每一轮都重发整段对话加上每个工具结果。这些在工具内部都看不见；而只要有东西站在工具和守护进程之间，它们就全部体现在守护进程自己的数字里。

观测端口就是这个东西：一个长得和 Ollama 一样的替身，把一切转发给真正的守护进程，并记下数字。

设置 ​

页面的空状态就是设置。它显示一个地址，默认是：

http://localhost:11435

凡是工具要求填 Ollama 地址的地方，都填它。页面为每个常见工具列出了确切的字段：

工具地址填在哪里
VS Code Copilot从 Marketplace 安装 Ollama 扩展（发布者 Ollama）；VS Code 旧的内置 Ollama 提供方已弃用。然后在设置中修改 ollama.endpoint，或在 Chat: Manage Language Models 中打开 Ollama 修改 URL。运行 Ollama: Refresh Models，在模型选择器的 Ollama 一栏中选择模型。
Open WebUI管理面板，设置，连接，Ollama API URL。在 Docker 容器中用 http://host.docker.internal:11435。
Continueconfig.yaml 中每个 Ollama 模型的 apiBase。
n8nOllama 凭据的 Base URL。
Python / curlollama.Client(host='http://localhost:11435')，OpenAI SDK 用 base_url='http://localhost:11435/v1'，命令行用 export OLLAMA_HOST=localhost:11435（PowerShell 用 $env:OLLAMA_HOST = "localhost:11435"）。

从工具发一条消息。页面会自动切换到实时视图。没有保存按钮，不用重启。

这个端口的行为与 Ollama 完全一致，包括根路径的欢迎语，所以那些在信任服务器前会探测 / 或 /api/tags 的工具看到的就是一个守护进程。模型的拉取、列表和删除直接通过、不做记录；只保留模型轮次（/api/chat、/api/generate、/api/embed，以及 OpenAI 兼容的 /v1/chat/completions、/v1/completions、/v1/embeddings）。

更改或关闭端口 ​

bash
npx llmxray --observe-port 11500   # 换一个端口
npx llmxray --no-observe           # 不打开它

在 Docker 中映射该端口（-p 11435:11435），并使用 OBSERVE_PORT 或 OBSERVE=0。如果默认端口已被占用，页面会说明，LLMxRay 的其余部分照常工作。

实时视图 ​

发现 ​

页面顶部是几句大白话，每句都链接到证明它的那一轮。只有证据足够时才会出现；一轮噪声数据永远不会触发。

  • 「客户端 发送的提示词有 N 个 token，但 模型 是以 M token 的上下文加载的。」 守护进程直接拒绝了请求，并在回复中给出了这两个数字，因此一轮就足以证明。解决办法是 Ollama 设置中的上下文长度；编程助手需要 32K 到 64K，而更大的上下文必须能和权重一起放进显存。
  • 「客户端 在这一轮与 模型 的对话中丢掉了缓存：上一轮保留 X%，这一轮 Y%。」 针对单独一轮，而非中位数：该客户端原本命中缓存，而这一轮的缓存份额下降了四十个百分点或更多。句子给出提示大小，以及提示从哪个 token 开始与上一轮不同。每个客户端与模型只显示最近一次这样的下降。
  • 「客户端 使用 模型 时每轮重读约 N 个 token。」 至少三轮的缓存份额中位数低于一半，且重算部分至少 500 个 token。句子会指出提示词从哪个 token 开始与上一轮不同，前提是守护进程报告了可供换算的计数。
  • 「模型 有 N% 在 CPU 上运行。」 来自守护进程自己的加载报告（/api/ps）：已加载大小与显存中部分的对比。常见原因是上下文窗口已放不进权重旁边；常见解决办法是更小的上下文或量化的 KV 缓存。
  • 「工具模式占 客户端 每条提示词的 N%。」 工具定义占提示词超过四分之一，并给出观测轮次中实际用到的数量。它们位于稳定前缀中，因此会被缓存，但仍然占用上下文。

轮次流 ​

最新在前：时间、客户端与模式（提供了工具则为代理，否则为对话）、模型、提示词 token、以彩色条表示的缓存命中份额、预填充时间、生成速度、工具调用。缓存份额是唯一带颜色的列，前缀断裂的客户端隔着房间都能看见。

客户端根据 User-Agent 和请求形状命名。未知客户端保留其产品名；悬停可见原始头部。

单轮详情 ​

点击一行。

提示词的构成。 一条分成系统指令、工具模式、历史与工具结果、你的消息的色条，按守护进程的 token 计数缩放。切分按字符进行，所以是比例，不是分词器。

缓存在哪里断裂。 页面保留同一客户端、同一模型的上一条提示词，找出本条第一个不同的字符。KV 缓存只在共享前缀上存活，所以那一点正是复用结束、重算开始的地方。页面说明其后有多少 token，以及若变化部分放在最后，预填充本可以是多少，按本轮自身的预填充时间线性推算。

开启保留提示词文本后，会显示断裂点两侧的文本，绿色部分已缓存，红色部分未缓存。这告诉你哪个值动了：光标位置、时间戳、重排过的片段。

数字。 提示词 token、缓存 token、预填充时间及实际速率（未缓存 token 除以预填充时间，绝不用总数）、生成、工具调用、模型加载时的上下文及其中多少在 CPU 上、运行时、协议、User-Agent。

按客户端 ​

每个客户端一张卡片：轮次、token、工具调用、预填充总时长，以及修复缓存可省：若提示词在新消息之前一直保持缓存，这些轮次本可跳过的预填充时间。这是根据本次会话的数字推算的。缓存实验室通过重发提示词实测同一件事；本页只观测，所以说「约」。

隐私 ​

默认关闭：只在内存中保留本次会话的计数和时间。不向磁盘写任何东西。

保留提示词文本开启后，请求体会保存到你主目录下的文件中（~/.llmxray/observe/，每天一个文件），页面上会显示每个断裂点附近的文本。它还会在轮次下方解锁请求视图：把请求渲染成一段对话，每条消息一个区块并保留真实换行，工具调用以卡片显示，工具结果默认折叠，工具列表给出每个工具的名称、描述、参数数量和大小。缓存断裂点直接标在它所在的消息里。搜索框覆盖消息和工具，原始 JSON 标签页加上复制和下载按钮保证每个字节都可取回。关闭后，内存中保留的文本会被丢弃；文件会一直保留，直到你删除它们。

两种模式下都没有任何数据离开你的机器。观测端口只与 LLMxRay 启动时指定的 Ollama 地址通信，不与其他任何地方通信。

本页不做的事 ​

它不做分词（比例按字符，计数来自守护进程），不跨重启保留轮次，也不改动任何经过它的内容。它是一扇窗，不是一个过滤器。

最后这一点有一个看得见的后果。OpenAI 兼容端点上的流式请求不带 token 计数，除非客户端用 stream_options: { include_usage: true } 主动要求；Ollama 和 OpenAI 一样，只在被要求时才追加 usage 块。LLMxRay 不会替客户端加上这个选项，因为有些客户端会被多出来的那个块卡住。这类轮次在缓存列显示未报告，提示词构成仍然照常显示。原生 API（/api/chat、/api/generate）总是报告计数，Ollama 命令行、Ollama SDK 和 VS Code Copilot 的 Ollama 提供方用的正是它。
